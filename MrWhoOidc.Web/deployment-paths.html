Start Here

Choose the right deployment path before you touch a command.

If you are new to MrWhoOidc, do not start by guessing between repositories, compose files, and sample apps. Pick the track that matches what you are trying to achieve, then follow only that path.

Recommendation

Most first-time visitors should start with the prebuilt Docker path.

Use source build only if you need to change code, debug internals, or work as a contributor.

Rule

Follow one track at a time. The most common setup mistakes come from mixing commands from different paths.

Deployment Options

Five tracks, each for a different job.

Choose based on outcome, not on how advanced the names sound.

Prebuilt Setup

The default path for local evaluation, first production-style installs, and anyone who wants the smallest working stack.

Use this when: you want the published Docker image, PostgreSQL, bootstrap, and verification.

Do not use this when: you need local source changes or contributor workflows.

Open the prebuilt guide

Proxy TLS Termination

An operator path for reverse proxies and load balancers that present public HTTPS while the backend container stays on HTTP only.

Use this when: you do not want a local certificate inside the backend container.

Do not use this when: you are following the direct local HTTPS quickstart.

See the proxy TLS track

Prebuilt + Redis

An operator path for Redis-backed distributed features and lower PostgreSQL load under repeated token and metadata traffic.

Use this when: you want the published image path plus Redis.

Do not use this when: you only need the smallest possible evaluation install.

See the Redis track

Prebuilt + Examples

A guided way to move from a working issuer into real client integrations using the public demo applications.

Use this when: you want to see SPA, confidential web app, API, or non-.NET examples.

Do not use this when: you are still trying to finish the first bootstrap.

See the examples track

Source Build

The contributor and debugging path that builds local images from the source tree and runs the seeded development stack.

Use this when: you need to modify code, debug internals, or work with the dev stack.

Do not use this when: you just want the published image install.

Open the source-build guide

Quick Chooser

What are you trying to do?

Use the simplest path that solves the job.

This is the decision tree for newcomers.

  • If you want a working issuer quickly, start with Prebuilt Setup.
  • If public HTTPS terminates at your proxy and the backend should stay HTTP-only, continue with Proxy TLS Termination.
  • If you already completed the prebuilt path and want Redis-backed features, continue with Prebuilt + Redis.
  • If you want to integrate a real sample app after bootstrap, continue with Prebuilt + Examples.
  • If you need to change code or build locally from source, switch to Source Build.

Advanced Path

Proxy TLS Termination

Use this path when a reverse proxy or load balancer exposes the public HTTPS endpoint and the backend container should run on HTTP only with forwarded headers. This path does not require a local aspnetapp.pfx inside the backend container.

Use this path when

  • Your proxy or load balancer presents the public HTTPS certificate.
  • You want the backend container to stay on private HTTP.
  • You can configure trusted forwarded-header sources.

Core command

docker compose -f docker-compose.tls-termination.yml up -d

Set OIDC_PUBLIC_BASE_URL to the public https://... URL, configure known proxies or known networks when possible, and validate through the public proxy URL rather than the backend HTTP port.

Advanced Path

Prebuilt + Redis

This is still the published Docker image path in the MrWho repository. Start with the basic prebuilt setup, then switch to the Redis overlay when you want Redis-backed distributed features and lower database load under repeated token and metadata work.

Use this path when

  • You already have the base deployment working.
  • You want Redis-backed distributed features.
  • You are moving toward the production overlay baseline.

Core command

docker compose -f docker-compose.yml -f docker-compose.redis.yml up -d

If you want the hardened baseline with Redis already included, the next step after this track is the production overlay.

  • Repo-owned path guide: Deployment Paths
  • Full overlay reference: Docker Compose Examples
  • Operational guidance: Deployment Guide

Advanced Path

Prebuilt + Examples

This path assumes the issuer is already running from the published Docker image setup. From there, choose the demo that matches the integration problem you want to validate.

Recommended starting points

  • .NET MVC for the clearest end-to-end confidential client example.
  • React for a browser-only SPA using PKCE and PAR.
  • OBO Demo API for downstream API token validation.
  • Go or Kotlin/Spring if your target stack is not .NET.

What this track gives you

  • Real client configuration examples.
  • A concrete scenario matrix by stack and flow.
  • A clean bridge from bootstrap to integration work.

Start the issuer once, then follow the README inside the demo that matches your architecture.

  • Repo-owned path guide: Deployment Paths
  • Demo overview: MrWho demo applications
  • Base deployment path: Prebuilt Setup

Separate Track

Source Build

This is intentionally separate from the prebuilt image path. Use it only when you need the MrWhoOidc source repository, the seeded development stack, local image builds, or contributor workflows.

Use this path when

  • You need to debug internals or change code.
  • You want the seeded development tenant and sample apps.
  • You are working with the contributor workflow and local builds.

Do not mix these commands

Do not combine MrWho published-image commands with MrWhoOidc source-build commands in the same runbook. The page below keeps the contributor path separate on purpose.

Open the source-build guide
