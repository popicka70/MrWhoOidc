Advanced Path

Proxy TLS Termination

Use this path when a reverse proxy or load balancer exposes the public HTTPS endpoint and the backend container should run on HTTP only with forwarded headers. This path does not require a local aspnetapp.pfx inside the backend container.

Use this path when

  • Your proxy or load balancer presents the public HTTPS certificate.
  • You want the backend container to stay on private HTTP.
  • You can configure trusted forwarded-header sources.

Core command

docker compose -f docker-compose.tls-termination.yml up -d

Set OIDC_PUBLIC_BASE_URL to the public https://... URL, configure known proxies or known networks when possible, and validate through the public proxy URL rather than the backend HTTP port.

Advanced Path

Prebuilt + Redis

This is still the published Docker image path in the MrWho repository. Start with the basic prebuilt setup, then switch to the Redis overlay when you want Redis-backed distributed features and lower database load under repeated token and metadata work.

Use this path when

  • You already have the base deployment working.
  • You want Redis-backed distributed features.
  • You are moving toward the production overlay baseline.

Core command

docker compose -f docker-compose.yml -f docker-compose.redis.yml up -d

If you want the hardened baseline with Redis already included, the next step after this track is the production overlay.

Advanced Path

Prebuilt + Examples

Once your issuer is running, use a sample application to test sign-in and API access with your stack.

Recommended starting points

  • .NET MVC for a server-side web application using a confidential client.
  • React for a browser-only SPA using PKCE and PAR.
  • OBO Demo API for downstream API token validation.
  • Go if your target stack is not .NET.

Start the issuer once, then follow the README inside the demo that matches your architecture.
