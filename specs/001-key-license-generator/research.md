# Research: Key and License Management Service

**Date**: October 28, 2025  
**Feature**: Key and License Management Service  
**Branch**: 001-key-license-generator

## Purpose

Document technology choices, best practices, and design decisions for implementing a standalone key and license generation service for OIDC clients.

## Key Technology Decisions

### Decision 1: Storage Engine (SQLite vs PostgreSQL)

**Decision**: Use SQLite for key metadata persistence

**Rationale**:

- **Deployment simplicity**: SQLite is file-based, no external database server required
- **Low scale requirements**: ~100-1000 key records expected, minimal concurrent access
- **Container-friendly**: Single binary with embedded database, smaller image size
- **Sufficient features**: EF Core migrations, ACID transactions, full-text search all supported
- **Operational overhead**: Zero database administration, no connection pooling concerns

**Alternatives Considered**:

1. **PostgreSQL** (rejected):
   - Requires external database server or Aspire orchestration
   - Adds deployment complexity (connection strings, migrations across environments)
   - Overkill for simple key metadata (kid, algorithm, timestamps, status)
   - Constitution mandates PostgreSQL for MrWhoOidc.Auth, but this is a standalone service

2. **In-memory storage** (rejected):
   - Loses audit trail on container restart
   - Cannot persist key download history for compliance
   - No support for filtering/searching historical key generations

**Implementation Notes**:

- Use EF Core with SQLite provider
- Store SQLite database file in Docker volume for persistence
- Configure `PRAGMA journal_mode=WAL` for better concurrency
- Maximum database size expected: <10MB

### Decision 2: UI Framework (Razor Pages vs Blazor)

**Decision**: Use Razor Pages for web UI

**Rationale**:

- **Simplicity**: Form-based workflows (generate, download, list) with minimal interactivity
- **Performance**: Server-side rendering, smaller initial payload (~50KB vs ~2MB for Blazor WASM)
- **Consistency**: MrWhoOidc.WebAuth uses Razor Pages; maintains architectural consistency
- **Docker image size**: Razor Pages = ~200MB container, Blazor adds ~50-100MB for WASM runtime
- **Development velocity**: Faster iteration for simple CRUD forms without WebSocket/SignalR complexity

**Alternatives Considered**:

1. **Blazor Server** (rejected):
   - Requires persistent WebSocket connections (overkill for admin tool)
   - Higher memory footprint per user (circuit state)
   - Unnecessary complexity for simple form submissions

2. **Blazor WebAssembly** (rejected):
   - Large initial download (2-3MB .NET runtime)
   - Adds build complexity (AOT compilation, trimming)
   - No offline scenarios needed (admin tool requires server access)

**Implementation Notes**:

- Use ASP.NET Core 9.0 Razor Pages
- Anti-forgery tokens on all POST endpoints
- Minimal JavaScript for client-side validation only
- TailwindCSS or Bootstrap for styling (match MrWhoOidc.WebAuth style)

### Decision 3: Key Generation Algorithms

**Decision**: Support RSA (2048/3072/4096-bit) and ECDSA (P-256/P-384/P-521)

**Rationale**:

- **RFC compliance**: OpenID Connect Core supports RS256/RS384/RS512 (RSA) and ES256/ES384/ES512 (ECDSA)
- **Security best practices**: RSA 2048-bit minimum (NIST recommendation), ECDSA P-256 minimum
- **JAR/JARM compatibility**: Both RSA and ECDSA widely supported by OIDC implementations
- **Performance trade-offs**: ECDSA faster with smaller keys (P-256 = 256-bit key ≈ RSA 3072-bit security)

**Alternatives Considered**:

1. **RSA only** (rejected):
   - Excludes ECDSA use cases (smaller keys, faster signing)
   - ECDSA increasingly preferred for mobile/IoT clients

2. **Add RSA-PSS (PS256/PS384/PS512)** (deferred):
   - Less widely supported than RS256 family
   - Can add later if client demand exists

**Implementation Notes**:

- Use `System.Security.Cryptography.RSA.Create()` for RSA key generation
- Use `System.Security.Cryptography.ECDsa.Create()` for ECDSA key generation
- Generate unique `kid` using `GuidHelper.NewId()` (UUIDv7 for time-ordering)
- Export private keys as JWK (JSON Web Key) format
- Export public keys as JWKS (JSON Web Key Set) format with single key

### Decision 4: License Token Signing

**Decision**: Use existing ECDSA P-256 licensing private key (PEM format)

**Rationale**:

- **Continuity**: Maintains compatibility with existing license validation in MrWhoOidc.WebAuth
- **Security**: ECDSA P-256 provides 128-bit security level (sufficient for license signing)
- **Existing tooling**: Command-line `LicenseGenerator` uses same key and format
- **Key management**: Private key provided externally (Docker secret/volume), never generated by service

**Alternatives Considered**:

1. **Generate new signing key** (rejected):
   - Breaks compatibility with existing licenses
   - Requires distributing new public key to all installations

2. **Use RSA for signing** (rejected):
   - Existing key infrastructure uses ECDSA
   - No benefit over ECDSA for license signing use case

**Implementation Notes**:

- Load licensing private key from `appsettings.json` or environment variable (path to PEM file)
- Validate key on startup; fail fast if missing or invalid
- Use `System.IdentityModel.Tokens.Jwt` for JWT generation
- Include claims: `iss`, `nbf`, `iat`, `exp`, `jti`, `tier`, `organization`, `features`, `limits`

### Decision 5: Private Key Security

**Decision**: One-time download with no server-side storage of private keys

**Rationale**:

- **Security principle**: Private keys should never be persisted on server
- **Compliance**: Reduces attack surface and audit scope (no stored sensitive cryptographic material)
- **User responsibility**: Admins download private key immediately; it's their responsibility to secure it

**Alternatives Considered**:

1. **Store encrypted private keys** (rejected):
   - Encryption key management adds complexity
   - Server becomes target for private key theft
   - Violates principle of minimal privilege

2. **Provide download tokens** (deferred):
   - Could implement short-lived download URLs (5-minute expiry)
   - Not in MVP; private key download happens immediately after generation

**Implementation Notes**:

- Generate key pair in-memory during HTTP request
- Return private key as downloadable file (JWK JSON format)
- Immediately dispose of private key material from server memory
- Store only public key and metadata (kid, algorithm, timestamps)
- Log download events for audit trail (kid, timestamp, user)

## Best Practices

### Cryptographic Key Generation

**Sources**:

- NIST SP 800-57 Part 1: Key Management Recommendations
- RFC 7518: JSON Web Algorithms (JWA)
- RFC 7517: JSON Web Key (JWK)

**Key Practices**:

1. **Random number generation**: Use cryptographically secure RNG (`RandomNumberGenerator.Create()`)
2. **Key strength**: RSA ≥2048 bits, ECDSA ≥P-256 curve
3. **Key identifiers**: Unique `kid` for each key (UUIDv7 for time-ordering and collision prevention)
4. **Key usage**: Set `use` field in JWK (`sig` for signing keys)
5. **Algorithm specificity**: Always include `alg` field in JWK (e.g., RS256, ES256)

**Implementation Checklist**:

- [x] Use `System.Security.Cryptography` APIs (not third-party libraries)
- [x] Validate key parameters after generation (modulus length, curve parameters)
- [x] Export keys in standard JWK/JWKS format (RFC 7517)
- [x] Never log or transmit private key material except during immediate download
- [x] Dispose of cryptographic objects properly (`using` statements or `IDisposable`)

### EF Core Migrations with SQLite

**Sources**:

- EF Core documentation: SQLite provider
- SQLite documentation: WAL mode for concurrency

**Key Practices**:

1. **Migration generation**: Always use `dotnet ef migrations add` (never hand-write)
2. **Database location**: Store SQLite file in Docker volume path (e.g., `/data/keygen.db`)
3. **Concurrency**: Enable WAL mode (`PRAGMA journal_mode=WAL`) for better concurrent read/write
4. **Schema constraints**: Use unique indexes on `kid` field
5. **Data types**: SQLite stores GUIDs as TEXT; EF Core handles conversion automatically

**Implementation Checklist**:

- [x] Configure SQLite provider in `DbContext.OnConfiguring` or `Program.cs`
- [x] Use `GuidHelper.NewId()` for primary keys (UUIDv7)
- [x] Add unique index on `KeyPairMetadata.Kid` column
- [x] Configure cascade delete for `KeyDownloadRecord` → `KeyPairMetadata` relationship
- [x] Test migrations against SQLite database file

### Docker Containerization

**Sources**:

- Docker best practices: Multi-stage builds
- ASP.NET Core deployment guide: Docker

**Key Practices**:

1. **Multi-stage build**: Separate build and runtime images to minimize size
2. **Base images**: Use `mcr.microsoft.com/dotnet/aspnet:9.0` for runtime (Alpine for smallest size)
3. **Volume mounts**: Persist SQLite database file and licensing private key via volumes
4. **Environment variables**: Configure licensing key path via environment variable
5. **Health checks**: Add `/health` endpoint for container orchestration

**Implementation Checklist**:

- [x] Multi-stage Dockerfile (build → publish → runtime)
- [x] `.dockerignore` file to exclude `bin/`, `obj/`, `.git/`
- [x] Volume mount for `/data` (SQLite database)
- [x] Volume or secret mount for `/secrets` (licensing private key)
- [x] Expose port 8080 (HTTP) or 8443 (HTTPS)
- [x] Add `HEALTHCHECK` instruction in Dockerfile

## Open Questions (Resolved)

### Q1: Authentication/Authorization

**Question**: Should the service implement its own authentication, or rely on deployment-environment auth?

**Resolution**: Rely on deployment-environment authentication (reverse proxy, VPN, corporate network). This is an internal admin tool with low traffic; building custom auth is unnecessary complexity. Document deployment scenarios in README.

### Q2: Key Expiry/Rotation

**Question**: Should the service support automatic key expiry or rotation reminders?

**Resolution**: No. Key lifecycle is managed manually by administrators. The service provides key generation and audit trail; administrators decide when to rotate keys based on their security policies. Future enhancement could add expiry warnings.

### Q3: Multi-Tenancy

**Question**: Should the service support multi-tenancy (separate key namespaces per tenant)?

**Resolution**: No. This service is tenant-agnostic; it generates keys that clients associate with tenants in the OIDC server configuration. Multi-tenancy lives in MrWhoOidc.WebAuth, not in this admin tool.
