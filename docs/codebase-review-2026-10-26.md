## 1. Executive summary

This multi-tenant OIDC provider has substantial unit and browser-test coverage, container provenance, and documented internal security reviews. Tenant query filters normally fail closed when a DI-resolved context has no current tenant, with explicit exceptions for system scopes, contexts constructed without an accessor, and an emergency configuration option. Some credentials are still stored in plaintext (M-Plain); broad claims that every secret or key path is protected should not be treated as an exhaustive audit.

The genuine problems found are concentrated in four places:

1. **A correctness risk in the platform export/import API** — tenant filters can omit another tenant's configuration and tenant write guards can reject cross-tenant imports (the CLI depends on these endpoints).
2. **Test quality gaps that manufacture false confidence** — a DPoP test class that never invokes the DPoP validator, weak authorize/PAR negative assertions, and an e2e fixture that removes volumes on the configured Docker daemon regardless of `BASE_URL`.
3. **Inconsistent application of the codebase's own rules** — antiforgery on 4 of ~55 mutating admin endpoints; hashed bearer credentials in most paths but plaintext for QR auth codes and device codes; bounded Argon2 concurrency for client secrets but unbounded for user logins.
4. **Infra/CLI concerns** — MCP stdout protocol violation, a path-traversal file write via `Content-Disposition`, a config-corruption data-loss footgun, and an endpoint snapshot mismatch.

## 3. Findings by area (detail)

### 3.1 WebAuth HTTP surface

**H1 — Platform export/import under the wrong tenant filter.** `/admin/api/platform/tenants/{slug}/export` and `/admin/api/platform/tenants/import` are not under `/platform-admin`, so `PlatformSystemScopeMiddleware` does not open a system scope; root paths normally resolve to the default tenant. A non-default tenant's export can therefore omit filtered realm/client/provider data; imports containing entities for another tenant can be rejected by the write guard. Tests must use an accessor and exercise the real request and save paths: the bypass in `AuthDbContext.cs:1445-1448` is based on system scope, a missing accessor, or an opt-in setting, not on EF's InMemory provider as such. **Fix:** explicitly design authorized cross-tenant access for both reads and writes. `TenantFilterScope.BeginSystemScope()` bypasses the query filter, but `ApplyTenantWriteGuards()` still checks the current tenant; applying that scope alone does not fix imports. Add non-default tenant export, preview and import integration tests, including isolation and write-guard cases.

**CSRF (M-CSRF).** Minimal APIs do not inherit MVC's global antiforgery filter and the application does not call `UseAntiforgery`. Some client-secret endpoints use an explicit filter. Evaluate a consistent policy without accidentally exempting cookie-authenticated requests that merely carry an Authorization header.

**Other verified-clean areas:** discovery/JWKS (public payloads strip private JWK members), token endpoint orchestration (registered grant-type/auth-method enforced, centralized client auth), RFC 7591/7592 validation, admin CRUD tenant scoping (every read/mutation pins `TenantId == current`), platform-realm write guard (SaveChanges interceptor covering UI/API/import/seed), logout (confirmation page + antiforgery, verified `id_token_hint`, allow-listed post-logout URIs via single-use references), QR login (initiator-bound `__Host-` cookie, number matching, assignment+consent re-checked at confirm), external OIDC (browser-bound single-use state, back-channel ID token only, proof-of-ownership linking), SSRF posture (connect-time IP validation used consistently), cookie config (`__Host-`, 8 h absolute, stamp validation), CSP (nonce-based), support access (read-only enforced at three layers, durable audit, revocable).

### 3.2 Crypto, keys, licensing

**Verified clean / strong:**
- Argon2id (m=128 MiB, t=4, four lanes and one configured thread, 16-byte salt, 32-byte tag), password buffers zeroed, fixed-time compares, timing-equalized unknown-user path.
- The inspected signing-key paths use DataProtection, disable distributed caching for private keys, and sanitize public JWKS. This is evidence for those paths, not proof that every possible private JWK path has been audited.
- Key rotation now uses `pg_advisory_xact_lock` per tenant (`KeyRotationService.cs:94-120`) — the known-open C5 item is **resolved**.
- Licensing is ES256-only, re-verified on every load, fails closed to community tier, sublicense containment thorough, only a public key embedded; the committed e2e fixture key is properly isolated from production trust.
- Secret generation consistent `RandomNumberGenerator` throughout; refresh tokens/access tokens/auth codes/reset/invitation/DCR tokens all SHA-256 hashed at rest; TOTP replay protection + recovery codes with atomic single-use claims.
- DataProtection: production refuses an unencrypted key ring unless explicitly acknowledged.

**Medium findings:** unbounded login Argon2 concurrency (M-Argon2); plaintext QR auth code / device codes (M-Plain).

**Low:** no rehash-on-login for legacy `v1:` hashes (and unbounded parsed iterations); modulo bias in generated passwords; DPoP leeway-0 quirk; rotation overlap vs token lifetimes; enc-key never rotated; non-constant-time mTLS thumbprint compare.

### 3.3 CLI, examples, infrastructure

**Verified clean / strong:**
- CLI token/secret storage genuinely well engineered: 0600-at-creation files (no umask window), atomic temp-file+rename writes, DPAPI on Windows, honest plaintext-on-Linux with keychain as documented future work, legacy migration on save.
- Device-code login pins scope/resource to the admin API, same-origin-enforces token/discovery endpoints, https-except-loopback, RFC 8628 polling with `slow_down`, **zero `Process.Start` anywhere** (no command-injection surface).
- `--insecure` TLS bypass scoped to https loopback only, warns once, unit-tested.
- MCP security-conscious: read-only default, write tools unlisted when disabled, secrets redacted/0600-file'd, tenant-admin invite minting refused, all under test.
- CI/CD model-quality: SHA-pinned actions, no `pull_request_target`, per-job least privilege, SLSA provenance + SBOM, fail-closed host-key pinning, `:?` fail-closed compose interpolation, prod compose forwards all DataProtection settings (README warning satisfied), internal/edge network split, `.dockerignore` excludes certs/secrets.
- Examples teach the right patterns (TestApi validates iss/aud/signed; Go API has an `act` allowlist; RazorClient normalizes return URLs); no hardcoded secrets.

**Findings:** MCP stdout violation (Medium); `Content-Disposition` path traversal (Medium); config-corruption data loss (Medium); then the Low list in §2.

### 3.4 Tests & docs

**Genuine strengths:** `ParSecurityRegressionTests` and `UrlComparisonTests` pin real security behavior; refresh-token family semantics and tenant isolation have focused coverage (`TenantFilterFailClosedTests`, `DataIsolationTests`, `MultiTenantSecurityTests`, `AdminTenantIsolationTests`); `ClientScopeDefaultDenyTests` uses the real validator; WebAuthn crypto-level UV enforcement is tested with CBOR; and `AccountLinkingTakeoverTests` covers account-linking regressions. The original review spot-checked selected documentation claims; this was not an exhaustive documentation audit.

**Findings:** the four High/Medium test items in §2, plus: `Assert.Inconclusive` Redis-gated tests silently downgrade local coverage; empty `KeyGen.Tests/Test1.cs` placeholder; assertion-free "performance" test; duplicated `CryptoHelperTests` suites; a test that writes the endpoint snapshot into the source tree during runs (fragile in parallel CI).

**Coverage gaps:** additional real DPoP validator and integrated proof-enforcement semantics (H2; key-hardening tests already exercise the production validator); BackchannelLogoutDispatcher delivery/retry/poison; key-rotation overlap window + hosted service; CheckSession opbs; WebAuthn HTTP completion binding; concurrent code redemption on relational provider; e2e JWT signature verification.

### 3.5 Persistence & multi-tenancy

**H5 — `IDbContextFactory<AuthDbContext>` resolves the scoped `ITenantAccessor` from the root provider** (the original review reports a repro on EF Core 10.0.12; it was not independently rerun in this reassessment). `AddDbContextFactory` (`ServiceCollectionExtensions.cs:76`) + multiple `AuthDbContext` constructors can cause factory activation against the **root** provider. Consequences:
- **Development** (scope validation on): factory creation can throw on optional client/provider JWKS cache misses (`PublicJwksCache.cs:87,138,207`) and in `BackchannelAlertSampler`. The server `/jwks` uses scoped `IKeyStore` and is a separate path; the optional JWKS routes are disabled by default.
- **Production** (validation off): silently succeeds, and **all factory-created contexts share one root-scoped `TenantAccessor`** (`ReferenceEquals` across two created contexts = true). Current call sites defensively use `IgnoreQueryFilters()`, so there is no leak today — but the documented invariant ("every DI-resolved context receives an accessor", `AuthDbContext.cs:1429-1431`) is not actually held, and any future code that calls `SetTenant` on that shared instance would silently re-scope every factory context.
- **Fix:** use a factory with explicit scoped-lifetime ownership and add a root-provider scope-validation test. A null accessor bypasses the query filter and must not be used as a fail-closed shortcut.

**H6 — Missing lifecycle cleanup for several single-use tables.** `AuthorizationCode` rows have no general cleanup; expired/never-completed `DeviceCodeEntry` rows, logout redirect references, email confirmations and expired invitations also lack an expiry sweep. Denied and redeemed device entries are removed. Measure growth and query plans, then define retention before adding cross-tenant sweeps: authorization-code rows are used both for reuse detection and for selecting logout recipients.

**Medium:**
- **Expiry indexes** — `ExpiredTokenCleanupService` filters tokens by type and expiry; `AuthorizationCodes.ExpiresAt` has no index. Confirm actual plans before asserting a full scan. An index filtered on `RevokedAt IS NULL` does not cover the service's deletion predicate, which includes revoked tokens.
- **Public provider JWKS lookup is cross-tenant by name** (`PublicJwksCache.cs:138-141`): `IgnoreQueryFilters()` + name match, but provider names are unique only per tenant — two tenants registering the same provider name means the endpoint serves whichever row comes first; a tenant can shadow another tenant's provider keys. Fix: tenant-qualified cache key, tenant resolved from the `/t/{slug}` path.
- **`BackchannelLogoutDispatcher._circuits` is a plain `Dictionary` mutated from concurrent tasks** (`:61,136-138,363-391`; `Task.WhenAll` with configurable concurrency) — race on concurrent add and lost failure counts. Synchronize whole per-client state transitions, not only dictionary operations or increments.
- **`EnsureUserPrimaryKeysAvailableAsync` is a per-save defensive probe** (1–2 extra queries on every save adding users) patching a historical ID-collision bug; it goes through the tenant filter, so it can't even see cross-tenant collisions. Fix the root cause, then remove.

**Verified fixed (both known legacy items):**
- **D17 — tenant filter now fails closed** (`AuthDbContext.cs:1445-1448`): tenantless required-entity queries return zero rows; optional-entity filter shows only platform rows; escape hatch `MultiTenancy:TenantFilterFailOpen` defaults false; 8 focused tests including AsyncLocal-leak cases.
- **C5 — key-rotation cross-replica lock implemented** (`KeyRotationService.cs:94-120`): `pg_advisory_xact_lock` per tenant inside an execution strategy; provisioning locked the same way. Background jobs all cover every tenant (`ForEachActiveTenantAsync` or explicit `IgnoreQueryFilters` + system scope), BCL dispatch uses per-row claim leases (better than a job-wide lock), and cleanups are idempotent.

**Low:** retry-strategy replay can flag a legitimate auth-code redemption as reuse (rare, fail-closed); `TenantSupportAccessCleanupService` uses both an hourly delay and a periodic timer and re-queries sessions, but coalesced timer ticks mean the claimed half cadence is unproven; QR cleanup ignores expired `Pending` sessions; `TenantService.FindBySlugAsync` caches Suspended/Deleted tenants and cache invalidation misses the resolver key; whole `User` rows (incl. TOTP ciphertext) cached in Redis for 10 min (prefer a slim DTO); background audit events land as platform-wide (`TenantId=null`) rows visible in every tenant's audit views; `BackchannelAlertSampler` loads the whole window into memory, no index on `LastAttemptAt`.

**Selected strengths:** conditional persistence claims exist for authorization codes, PAR, device codes and several other artifacts; CIBA's tracked read/remove/save is an exception and needs relational concurrency testing. Protocol-critical unique constraints exist for code hashes, token hashes and other identifiers. Some transactional operations use execution strategies; not every multi-step grant does so (for example, device-code deletion and token issuance are separate operations). Signing-key protection, UUIDv7 entity IDs and a named database connection are also used.

### 3.7 Core OIDC protocol (`MrWhoOidc.Auth`)

The full authorization-code flow was traced end-to-end (`/authorize` → resolver → validator → code service → PAR consumption → `TokenHandler` → grant handler → `AuthorizationCodeExchanger`), plus client-credentials, refresh rotation, device, CIBA, RFC 8693 token exchange (incl. delegation), client authentication (secrets/assertions/mTLS/auth-method), PAR, consent, userinfo, introspection, revocation, and logout tokens.

**Medium findings:** M-Deact (deactivated users redeem pending codes), M-Aud (CC audience fail-open), M-TE-Aud (exchange bypasses M2M allow-lists), M-RT (offline_access — known/contested, see table).

**Verified clean / strong:**
- **Single-use claims:** auth-code claim uses conditional `ExecuteUpdate` inside a transaction, and reuse triggers user+client revocation (`AuthorizationCodeExchanger.cs:97-151`). Device redemption uses a conditional `ExecuteDelete`, but does not have the same transaction or reuse-revocation behavior (`DeviceCodeGrantHandler.cs:144-165`).
- **Refresh rotation is solid:** family advisory lock, atomic conditional claim, child born with family id, family-wide revocation under the lock, DPoP/mTLS `cnf` continuity checks (`RefreshTokenExchanger.cs:60-71,382-401`, `RevocationService.cs:168-214`).
- **Tenant isolation fails closed** on the token endpoint — cross-tenant code/token/client lookups are structurally impossible.
- **PAR done right:** client binding at resolution, single-use consumption inside the code-issuance transaction, full re-validation with the same validator as `/authorize`.
- **Registered `grant_types` + `token_endpoint_auth_method` are enforced**; the `AllowClientCredentials` open item is resolved (F15 below).
- **`claims` parameter cannot bypass scope gating** at `/authorize` (covering scopes added) or `/token` (the embedded userinfo-claims override is filtering-only — it can remove, never add).
- **JAR/request objects:** per-client + global alg allow-lists, replay cache, lifetime window, https-only SSRF-safe JWKS fetches; **fail-closed crypto plumbing** (ID-token encryption and JARM never fall back to plaintext); client assertions pinned to asymmetric algs with `exp` caps.
- **Consent flow** uses a one-time server-side challenge binding — no client-controllable scope injection.

**Low findings** (see the Protocol line in §2 Low): resource-introduction at token time; `token_type` mislabeled for DPoP-bound exchange tokens; CIBA non-atomic redemption (possible error under race; verify with a relational concurrency test); dead `/userinfo` roles resolution (no `azp`); `TokenValidator` revocation no-op without tenant; duplicate query params → 500; PKCE `plain` accepted-then-unredeemable for some confidential clients; CC mTLS binding from raw cert; legacy audience-free refresh tokens.

**Code quality:** heavy near-copy duplication between `AuthorizationCodeExchanger` and `RefreshTokenExchanger` (entitlements, license tokens, role queries, persistence — extract a shared issuance service); `MapJwaToSecurityAlgorithms` triplicated; inconsistent error model (tuple-based payloads, inline anonymous objects, a **403 with `invalid_grant`** for deactivated users on refresh — non-standard); null-forgiving `client!` → NRE/500 if the client row vanishes mid-flow (`AuthorizationCodeExchanger.cs:297-298`); `InMemoryJarReplayCache` O(n) scan on every add; device/CIBA grant handlers duplicate ~150 lines (the divergence already produced the CIBA race); dual `audience`/`resource` parameters triple the validation surface; `ClientStore.ValidateClientSecretAsync` hashes every active secret per attempt (timing-uniform but N× Argon2 cost); the Redis-cached `Client` entity includes the legacy `ClientSecretHash`.
